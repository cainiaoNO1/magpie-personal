### 1.2 窗口机制

Antigravity 的额度分两级窗口，两级的**计时起点都不是自然时刻，而是「这一次的第一次调用」**：

- **5 小时窗口**：重置后计时并不开始；**第一次真正用掉额度的调用**发生时才起算，5 小时后重置；
- **7 天窗口**：同上，7 天后重置；
- **一次调用同时把所属池的两个窗口钉住**（实测 `claude-sonnet-4-6`：5 小时 0 → 0.0015、7 天 0 → 0.0008，两个 `resetsAt` 都落在调用时刻 + 窗口长度）。所以有 5 小时窗口的池，盯住 5 小时窗口就够，7 天不用单独开；
- **例外是没有 5 小时窗口的池**：实测 `Gemini 4 Argon` 只有 7 天桶。这个池只能用它的 7 天窗口判定和开窗。

由此推出本需求的核心动机：**账号闲置不用时，窗口永远不会开始，额度也不会往前走**。7 天窗口一旦重置，如果没人调用，那 5 小时窗口就一直停在「满额未开」的状态；等到有人真用的时候才开始计时，5 小时的可用量被人为推迟。

> 这条「窗口从重置后的第一次调用起算」的规则，仓库对同类订阅已有同样的注释与实现：Claude 见 `internal/provider/claude_warmup.go:5-6`（`a Claude window, the 5-hour one and the weekly one, starts at the account's first request after it resets`），Codex 见 `internal/provider/codex_warmup.go:3-6`。Gemini / Antigravity 的这条规则本身是用户陈述，见 §7 A1、A2 待实测确认。

## 2. 问题陈述

### G1 — 闲置账号的窗口不会开始

没人调用，5 小时窗口就一直「未开始」，额度不往前推进。想用的时候才起算，等于把 5 小时的可用量整体推迟到「想用」的那一刻。

### G2 — 没有「未开始」的判定，也没有人替它做第一次调用

`QuotaWindow.Used` 是上游 `remainingFraction` 换算来的百分比（`internal/provider/google.go:1250-1251` `w.Used = (1 - *b.RemainingFraction) * 100`）。`Used == 0` 就是「一点没用」。仓库里已有把「未开始」读出来的原语 `notStarted`（`internal/provider/codex_warmup.go:655`），但它只为 Codex / Claude 的 warm-up 服务（`:620` `onNotStarted`、`:638` `usageRead`），没有任何 Antigravity 的消费者。

### G3 — 看不到「这个账号的窗口现在是什么状态」

账号卡片能显示 `used` 与 `resetsAt`，但没有「窗口是否已开、上次探测是什么时候、下次什么时候再探」的呈现。多账号轮转时只能靠人工记忆。

### G4 — 探测必须是一次真实的、可被计量的调用

如果开窗调用绕过网关直接打上游，它不会出现在用量账本里，也就无法在 `/api/usage/requests` 里核对自己到底发了什么、花了多少。见 §6 D2 的取舍。

## 3. 目标与非目标

### 目标

1. 按账号、按配置的间隔，**定时读取每个池**的用量；
2. 某个池「未使用」时，**自动用该池的一个模型发出一次极小的真实调用**，把那个池的计时开起来；
3. 某个池「已使用」时，不再打扰，等到下一次随机间隔再看；
4. 侧边栏新增独立页面 `Gemini`，展示每个 Antigravity 账号的窗口状态、探测时间线，并能按账号 + 时间区间查看用量；
5. 全部行为可通过设置开关与间隔控制，关掉即完全静止。

### 非目标（本轮不做）

- **不做有 5 小时窗口的池的「7 天单独开窗」**：一次调用同时钉住两个窗口（§1.2），探 5 小时即覆盖。只有没有 5 小时窗口的池（Argon）才由 7 天窗口判定；
- **不改路由与排序**：不新增 `Rest` 原因，不改 `Allowances`（`internal/provider/routing.go:484`）的取舍；
- **不改上游 `docs/` 覆盖的子系统语义**：本需求只新增后台循环 + 一个页面插件 + 两条 HTTP 路由；
- **不做多 magpie 实例的协调**：状态文件是本机的，两台 magpie 各自开各自的窗；
- **不为认不出的池开窗**：页面上画出来、标「未监视」，不调用（见 §7 A3）。

## 4. 术语

| 术语 | 含义 |
| --- | --- |
| **窗口（window）** | 一份额度，有长度（5 小时 / 7 天）与重置时刻 |
| **开窗（start a window）** | 发一次真实调用，让「重置后第一次调用」发生，计时从此起算 |
| **未使用（not started）** | 该窗口 `Used == 0` 且没有已知重置时刻：一点额度都没被用掉 |
| **池（pool）** | 一组共享同一份额度的模型。实测有 `Gemini`、`Claude & GPT`，部分套餐还有 `Gemini 4 Argon`（`internal/provider/google.go:1193-1200`、`:1225` `poolName`） |
| **首字调用** | 开窗那一次调用；本设计里它是一个真实的 `POST /v1/chat/completions`，走网关 |
| **随机间隔** | 配置的间隔 N 是**上界**，实际等待落在 `[0.8N, N]` |

## 5. 需求清单

### R1 · 定时读取 5 小时窗口

**要求**：后台循环按账号逐个读取 5 小时窗口的用量，间隔由设置决定，默认 5 分钟，最小 1 分钟。

**验收**：

- [ ] 开启后，每个 Antigravity 账号每 N 分钟被读一次，N 取设置值；
- [ ] 实际间隔是随机的，落在 `[0.8N, N]`，不同账号不同步；
- [ ] 关闭后不再有任何读取与调用，进程日志无新增；
- [ ] 读取失败（网络、401、上游 5xx）不导致循环退出，下个周期继续。

### R2 · 「未使用」时自动开窗

**要求**：读到某个池的判定窗口（有 5 小时窗口就是它，没有就是 7 天窗口）`Used == 0` 时，立即用**这个池自己的模型**发一次极小调用；模型一律从账号自己的列表里挑，`max_tokens` 极小。`Gemini` 池选**真正计进它**的 `gemini-3.8-flash`（账号没列这个家族时才退回该账号最便宜的 flash-lite）；`Claude & GPT` 池优先 `sonnet`，其次 `claude`，再次 `gpt-oss`；`Gemini 4 Argon` 池要 `gemini-4-argon` 本身（`-disabled` 除外）。**「最便宜」不是判据**：实测 2.5 / 3 / 3.1 / 3.5 的 flash 家族不动 5 小时计数，见 `技术设计文档.md` §3.4；模型也**不能写死**，pix 账号明确拒绝 `claude-sonnet-4-6`、列的是 `claude-sonnet-5-5`。

**验收**：

- [ ] 每个未使用的池在一个周期内收到恰好一次开窗调用，不是多次；一个账号几个池就几次；
- [ ] 开窗调用在用量账本里可见（`/api/usage/requests` 能查到），且被标为 magpie 自己的调用；
- [ ] 调用成功（HTTP 200）后，下一轮读取看到 `Used > 0`，不再开窗；
- [ ] 该账号列表里没有这个池的模型时，跳过这个池并记下原因，不报错重试；认不出的池一次都不调。

### R3 · 已使用时只读不动

**要求**：读到 `Used > 0` 时，本轮不发任何调用，只记录读数与下次时刻。

**验收**：

- [ ] 已开窗的账号在两个连续周期内都不产生调用；
- [ ] 页面上该账号的状态从「未开窗」变为「已开窗」，并显示最近一次读数时刻。

### R4 · 状态可见

**要求**：`GET /api/gemini/custom` 返回每个账号一行：账号、窗口列表、上次检查时刻、下次检查时刻、上次开窗时刻、尝试次数、最近一次 HTTP 状态、最近一次错误。

**验收**：

- [ ] 每个 Antigravity 账号恰好一行；
- [ ] 从未探测过的账号，`lastCheck`/`nextAt` 为空而不是零值时间；
- [ ] 错误以人话呈现，不吞掉。

### R5 · 设置可改、立即生效

**要求**：`POST /api/gemini/custom` 接受 `{on, every}`；`every` 为秒，0 表示用默认值；小于最小值时拒绝并说明。

**验收**：

- [ ] 关闭后循环在下个 tick 内停止动作；
- [ ] 改间隔后无需重启，新间隔在下个周期生效；
- [ ] 设置写进 `settings.json`（`geminiWatch` 字段），重启后仍在；
- [ ] `every` 小于 60 时返回 400 并给出最小值。

### R6 · 页面：汇总与详细信息

**要求**：新页面按账号展示汇总（调用数、token、成本），并可展开到该账号的逐条请求。

**验收**：

- [ ] 汇总按「该账号 + 5 小时区间」聚合；
- [ ] 详细信息列出同一区间内的逐条请求，可点开看单条；
- [ ] 7 天视图与 5 小时视图可切换，两者口径一致；
- [ ] 账号与区间切换不刷新整页。

### R7 · 与现有机制共存

**要求**：不破坏既有 warm-up、路由与额度卡片。

**验收**：

- [ ] Codex / Claude / WorkBuddy 的 warm-up 行为不变；
- [ ] 额度卡片上 Antigravity 的展示不变；
- [ ] 新增脚本不进入核心体积预算（见 §6 D7）；
- [ ] 新增文案四种语言齐全（zh / zh-TW / ja / de，`internal/gui/assets/i18n.js:6,3882,7743,11606`）。

## 6. 已定决策

| # | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 界面形态 | **侧边栏新增独立页面 `Gemini`**，不塞进 Usage 页 | Usage 页已经很重（`internal/gui/assets/plugins/usage/page.js` 3287 行）；独立页面插件是仓库既定做法（`plugins/custom/custom.go:13-29`），新增文件不进核心体积预算 |
| D2 | 开窗调用走哪条路 | **走本机网关**（`POST /v1/chat/completions`，`internal/gateway/gateway.go:734`），作为一次真实请求 | 只有走网关，这次调用才会被路由、被代理、被记进用量账本，事后可核对。直连上游则账本里查不到（G4） |
| D3 | 怎么算「已使用」 | **读上游额度**：池的判定窗口（有 5 小时就是它，没有就是 7 天）`Used > 0` 即算已使用 | 权威信号优先于本地推算，与 `doc/workbuddy/技术设计文档.md:35-40` 的原则一致；`Used` 由上游 `remainingFraction` 直接换算（`internal/provider/google.go:1250-1251`） |
| D4 | 开窗用什么模型 | **每个池各挑一个**，都从账号自己的列表里挑：`Gemini` 池 `gemini-3.8-flash`（其次 `-tiered`，再次最便宜的 flash-lite）；`Claude & GPT` 池优先 `sonnet`、其次 `claude`、再次 `gpt-oss`；`Gemini 4 Argon` 池要 `gemini-4-argon` 本身。`max_tokens` 极小 | 开窗只需要「一次成功的调用」，但**得是计进 Gemini 池的那次**。原结论「最便宜的 gemini flash」被实测推翻：2.5 / 3 / 3.1 / 3.5 家族不动 5 小时计数，只有 3.8-flash（及 `-tiered`）动；挑便宜的那个会每轮白开一次窗。全表见 `技术设计文档.md` §3.4 |
| D5 | 间隔语义 | 配置值 N 是**上界**，实际等待在 `[0.8N, N]` 随机 | 多账号不同步，避免同一分钟一起打上游；N=5 分钟时实际 4–5 分钟 |
| D6 | 账号范围 | **只列 Antigravity 账号**，Gemini 订阅不列 | 只有 Antigravity 有 5 小时 + 7 天的池窗口（`internal/provider/google.go:1184-1186` 只在 `agent == "antigravity"` 时追加 `pools`） |
| D7 | 前端代码放哪 | 新页面插件 `gemini`，脚本在 `internal/gui/assets/plugins/gemini/` 下 | 插件的 `Client` 文件不计入核心预算（`internal/gui/core_budget_test.go:18-19` 只算 `app.js` 与核心脚本） |
| D8 | 在哪儿改、在哪儿测 | **在 `18.188.150.249` 上改、编译、测**，本地不编译 | 本地 Mac 没有 Go 工具链；服务器上是 Go 1.27.3，与 `go.mod:3` 的 1.26.8 兼容（向下兼容） |

## 7. 待验证假设

| 编号 | 假设 | 验证方式 | 不成立时的影响 |
| --- | --- | --- | --- |
| **A1** | 5 小时窗口确实从「重置后第一次调用」起算，而不是自然时刻 | 在 150 上对一个闲置账号观察：不调用时 `resetsAt` 是否推进；开窗后 5 小时是否精确对应 | 若为自然时刻，整个「定时开窗」需求失去意义，本设计退化为纯展示 |
| **A2** ✅ 已实测 | 7 天窗口重置会连带重置 5 小时窗口 | 2026-11-02 实测：一次 `claude-sonnet-4-6` 调用把 `Claude & GPT` 的 5 小时与 7 天 `resetsAt` 都钉在调用时刻 + 各自的窗口长度 | 成立。没有 5 小时窗口的池（Argon）是例外，只能用它的 7 天窗口判定 |
| **A3** ✅ 已实测 | `Gemini` 池与 `Claude & GPT` 池各自独立计时 | 2026-11-02 实测：`gemini-3.8-flash` 只动 `Gemini`（`Gemini 4 Argon` 的 7 天跨过这次调用不变）；`claude-sonnet-4-6` 只动 `Claude & GPT`；`gemini-4-argon` 动 `Gemini 4 Argon`，同时**也**动 `Gemini` | 成立，所以每个池要自己的模型、自己的判定。注意 Argon 不是反过来的隔离 |
| **A4** | `max_tokens` 会被上游接受并真正限制输出 | 在 150 上发一次 `max_tokens: 1` 的请求，看响应与用量 | 见 §8 已知偏差 3：Antigravity 的 gemini 模型路径上 `max_tokens` 不会被转发，实际靠「提示词只有一个 hi」把输出压短 |

> A1 是**影响最大**的假设：它决定整个需求是否存在。建议第一个验证。

## 8. 已知偏差（源码与最初设想不一致处）

以下四处是在读源码时发现的、与「按现有接口直接取数」的设想不一致的地方。**记录在案，不粉饰**；对应处理见 `技术设计文档.md` §3.7 与 §4.4，以及 `定时开窗设计.md` §5.6。

| # | 偏差 | 证据 | 处理 |
| --- | --- | --- | --- |
| 1 | `GET /api/usage` **只读 `period`**，传 `account` / `provider` 会被静默忽略，拿不到「按账号过滤的汇总」 | `internal/gui/usage.go:100-102`：`usageState(periodOf(r.URL.Query().Get("period")))`，没有任何 `Filter` 参与；`usageapi.Page` 签名只收 `Period`（`internal/usageapi/usageapi.go:75`） | 汇总数字改从 `/api/usage/requests` 的 `Totals` 取（该合计本身按 filter 过滤），不用 `/api/usage`。见 `技术设计文档.md` §4.4 |
