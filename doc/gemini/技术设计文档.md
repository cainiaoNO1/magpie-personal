> 目标仓库：`magpie-personal`（单仓库，无插件侧改动）

## 1. 总体思路

**读上游的权威读数，只在「读数说没用过」时才动一次手。**

```
                        ┌──────────────────────────────────┐
                        │  Antigravity 上游                 │
                        │  retrieveUserQuotaSummary         │
                        │  · 5h 桶 remainingFraction        │
                        │  · weekly 桶 remainingFraction    │
                        └───────────────┬──────────────────┘
                                        │ internal/provider/google.go:1220 call()
                        ┌───────────────▼──────────────────┐
                        │ provider.pools()                  │
                        │ QuotaWindow{Pool, Span, Used, ...}│
                        └───────────────┬──────────────────┘
                                        │
        ┌───────────────────────────────▼───────────────────────────────┐
        │ provider.KeepGeminiWarm（新，后台循环，每 N 分钟一次）          │
        │                                                               │
        │  读到 5h 窗口 Used == 0 且无重置时刻                            │
        │      ├─ 是 → 发一次「首字调用」→ POST 本机 /v1/chat/completions  │
        │      └─ 否 → 只记录，等下个随机间隔                              │
        └───────────────────────────────┬───────────────────────────────┘
                                        │ 状态写 gemini-warmup.json
                        ┌───────────────▼──────────────────┐
                        │ GeminiRows(now)                   │
                        │ GET /api/gemini/custom            │
                        └───────────────┬──────────────────┘
                                        │
                        ┌───────────────▼──────────────────┐
                        │ 页面插件 gemini（侧边栏独立页）    │
                        │ 汇总 / 详细信息（复用 usage 接口） │
                        └──────────────────────────────────┘
```

**设计原则**

1. **权威优先**：窗口用没用过，只信上游读数（`internal/provider/google.go:1250-1251` 由 `remainingFraction` 换算），不在本地推算。
2. **复用既有形状**：循环、状态文件、原子写、随机等待，全部照 `internal/provider/workbuddy_warmup.go` 与 `codex_warmup.go` 的既有做法，不新造一套。
3. **只加不改**：不改 `Allowances`（`internal/provider/routing.go:484`）、不改 `Rest` 语义、不改额度卡片渲染。
4. **一次动作，一次记录**：开窗调用走网关（`internal/gateway/gateway.go:734`），因此它出现在用量账本里，可核对。

## 2. 数据模型

### 2.1 复用现有结构（不改）

```go
// internal/provider/subscription_usage.go:29
type QuotaWindow struct {
    Unlimited bool       `json:"unlimited,omitempty"`
    Name      string     `json:"name"`
    Used      float64    `json:"used"`          // 百分比，上游 remainingFraction 换算
    ResetsAt  *time.Time `json:"resetsAt,omitempty"`
    ResetSecs int64      `json:"resetSecs,omitempty"`
    // ...
    Family string `json:"family,omitempty"`     // internal/provider/google.go:1175
    Pool   string `json:"pool,omitempty"`       // internal/provider/google.go:1225/1234
    Span   time.Duration `json:"-"`             // :65 —— 不进 JSON
    Model  string        `json:"-"`             // :66 —— 不进 JSON
    Aside  bool          `json:"-"`             // :67 —— 不进 JSON
}
```

> **注意**：`Span` / `Model` / `Aside` 都是 `json:"-"`（`internal/provider/subscription_usage.go:65-67`）。前端拿到 `used` / `resetsAt` / `pool` / `family`，但**拿不到窗口长度**。所以「这个窗口是 5 小时还是 7 天」必须由服务端明确给出——`GeminiRow` 的每个池带着自己那几扇 `Windows`，池的归属也由服务端分好，不能靠前端从 JSON 里推。

5 小时池窗口的构造在 `internal/provider/google.go:1234-1239`：

```go
w := QuotaWindow{Pool: pool, Used: 100, Aside: true}
switch strings.ToLower(b.Window) {
case "5h":
    w.Name, w.Span = "5 hours", 5*time.Hour
case "weekly":
    w.Name, w.Span = "7 days", 7*24*time.Hour
}
```

`Used` 默认 100（当作「用光了」），只有拿到 `RemainingFraction` 才改写（`internal/provider/google.go:1250-1252`）。**因此「上游没给这个桶的读数」和「用光了」在结构上是同一个值** —— 判定「未使用」时必须同时要求 `ResetsAt == nil`，否则会把「读数缺失」误判成「用光了」，反过来也一样。

### 2.4 状态文件

沿用 `workbuddy-warmup.json` 的位置与写法（`internal/provider/workbuddy_warmup.go:120`）：

```go
// 与 codex-warmup.json / workbuddy-warmup.json 同级
func geminiWarmPath() string { return filepath.Join(filepath.Dir(Path()), "gemini-warmup.json") }
```

`filepath.Dir(Path())` 是配置目录（`internal/provider/provider.go:455` `Path()` 返回 `<config>/providers.json`）。落盘用「写临时文件 + rename」，照 `internal/provider/workbuddy_warmup.go:133-144`：

```go
tmp := path + ".tmp"
if err := os.WriteFile(tmp, b, 0o600); err != nil { return }
os.Rename(tmp, path)
```

**原子写不是可选项**：这个文件每个周期都被改写，进程随时可能被重启（Docker `restart`）。写一半的文件会让下一轮 `json.Unmarshal` 失败——读侧已经按「读不出来就当空的」处理（`internal/provider/workbuddy_warmup.go:124-130` 的 `readWBWarmState`），丢一次状态只是让账号多探一次，不会更糟。

## 3. 关键流程

### 3.1 循环的启动

挂到 `internal/gateway/gateway.go:548` `ListenAndServe` 的 goroutine 块里，紧挨 `:620-621` 的 WorkBuddy 两行：

```go
provider.SetGeminiWatch(geminiWatchOf(settings.Load().GeminiWatch))
go provider.KeepGeminiWarm(ctx)
```

**为什么在这里**：这个块里的每个循环都满足「只有真正在跑网关的那个 magpie 才做」（`internal/gateway/gateway.go:603-604` 的注释说得明白：`the magpie serving the gateway, and only it, keeps the saved accounts signed in`）。开窗必须在有网关的实例上做——因为开窗调用就是打给这个网关的。

**设置的热更新**：`SetGeminiWatch` 由两处调用——启动时读一次 `settings.Load()`，以及 `POST /api/gemini/custom` 之后（照 `internal/gui/workbuddy_custom.go:116` 的 `applyWorkBuddyWatch` 模式）。循环每轮重新读一次当前设置，因此关掉之后下一个 tick 就不动作，不需要重启。

### 3.2 一轮做什么

```
每个 tick（间隔 1 分钟，与 wbWarmEvery 同量级）：
  1. w := 当前设置；if !w.On { continue }
  2. for each Antigravity 账号（googleLogins("antigravity")）:
       a. 到点了吗？now < 该账号的 NextAt → 跳过
       b. 读该账号的额度（loginQuota → googleLoginQuota）
       c. 从读数里挑出 5 小时窗口（Span == 5h 且 Pool != ""）
       d. 判定：
            Used == 0 && ResetsAt == nil && ResetSecs <= 0  → 未使用
            其它                                            → 已使用（或读数不可判）
       e. 未使用 → 发一次首字调用（§3.3），记 LastCallAt / Status / Err
          已使用 → 只记 LastCheck
       f. NextAt = now + rand(0.8N, N)
```

判定函数直接复用仓库已有的 `notStarted` 形状（`internal/provider/codex_warmup.go:655-657`）：

```go
func notStarted(w QuotaWindow) bool {
    return w.Span > 0 && !w.Aside && w.Model == "" && w.Used == 0 && w.ResetsAt == nil && w.ResetSecs <= 0
}
```

> **注意 `Aside`**：池窗口在 `internal/provider/google.go:1234` 被构造为 `Aside: true`（因为「用光它不会让账号停摆」，见 `internal/provider/subscription_usage.go:60-64` 的字段注释）。而 `notStarted` 要求 `!w.Aside`。**因此不能直接对池窗口调 `notStarted`** —— 这是本设计最容易被照抄错的一处。Gemini 的判定必须是自己的：

```go
// geminiNotStarted is a pool window that has never been used: nothing
// used, no reset known. Aside is what a pool window is (internal/provider/google.go:1234),
// so it is not asked for here.
func geminiNotStarted(w QuotaWindow) bool {
    return w.Span == 5*time.Hour && w.Pool != "" && w.Used == 0 && w.ResetsAt == nil && w.ResetSecs <= 0
}
```

### 3.3 首字调用

走本机网关，照 `internal/provider/workbuddy_warmup.go:527-562` `wbProbe` 的形状：

```go
func geminiFirstCall(ctx context.Context, account, model string) (int, error) {
    if gatewayURL() == "" {
        return 0, fmt.Errorf("the gateway's address isn't known yet")
    }
    ctx, cancel := context.WithTimeout(ctx, geminiCallTimeout) // 60s
    defer cancel()
    body, _ := json.Marshal(map[string]any{
        "model":      model,
        "messages":   []map[string]string{{"role": "user", "content": "hi"}},
        "max_tokens": 1,
    })
    req, _ := http.NewRequestWithContext(ctx, http.MethodPost, gatewayURL()+"/v1/chat/completions", bytes.NewReader(body))
    req.Header.Set("Content-Type", "application/json")
    req.Header.Set("X-Magpie-Account", account)          // internal/gateway/gateway.go:6474 AccountHeader
    req.Header.Set("User-Agent", "magpie-gemini-warmup/1")
    resp, err := http.DefaultClient.Do(req)
    ...
}
```

三个头部各有用途：

| 头部 | 用途 | 依据 |
| --- | --- | --- |
| `X-Magpie-Account` | 钉住账号，不让路由换人 | `internal/gateway/gateway.go:6474` `AccountHeader`；钉住后若账号在休息，`internal/gateway/fallback.go:3239` `pinTo` 直接返回 429，不换账号（这正是我们要的：换人开窗等于开错账号的窗） |
| `User-Agent: magpie-gemini-warmup/1` | 让这次调用在账本里被认成 magpie 自己的 | `internal/usage/usage.go:713-720` `ByMagpie()`：`id == "magpie" 或 strings.HasPrefix(id, "magpie-")` |
| `max_tokens: 1` | 尽量压短输出 | **但见 §5 的「`max_tokens` 不生效」一行**：Antigravity 的 gemini 模型路径上它不会被转发 |

**为什么不用 `provider.Fetch` 直连上游**：WorkBuddy 的探测之所以直连，是因为网关自代理会被 `pinTo` 拒（见 `doc/workbuddy/免费额度解冻探测设计.md` §2 的「固定账号的自代理走不通」一行）。Gemini 这里反过来——**要走网关**，理由见 PRD D2：只有走网关，这次调用才进账本、才可核对、才算「真的用了一次额度」。这也与 Codex 的 warm-up 一致（`internal/provider/codex_warmup.go:3-6` 注释：`sends that account one tiny request, as the gateway sends any`）。

### 3.4 模型怎么挑

**不是最便宜的那个，是「开得了窗」的那个。** 这一节原本写的是「该账号上最便宜的 gemini flash 模型」，那是错的，实测推翻了它。

在 150 上逐模型实测（各发一次请求，比 Gemini 池 5 小时窗口的 used 前后）：

| 模型 | 发出的 token | 5 小时 used 前 → 后 |
| --- | --- | --- |
| `gemini-2.5-flash-lite` | 2157 | 0.0164 → 0.0164（没动） |
| `gemini-2.5-flash-lite` | 991 | 0.0176 → 0.0176（没动） |
| `gemini-2.5-flash` | 12 | 0.0502 → 0.0502（没动） |
| `gemini-3-flash` | 1167 | 0.0176 → 0.0176（没动） |
| `gemini-3.5-flash-lite` | 11 | 0.0435 → 0.0435（没动） |
| `gemini-3.1-flash-lite` | 12 | 0.0176 → 0.0176（没动） |
| `gemini-3.8-flash` | 1325 | 0.0000 → 0.0164（**动了**） |
| `gemini-3.8-flash` | 1950 | 0.0176 → 0.0419（**动了**） |
| `gemini-3.8-flash` | 97 | 0.0164 → 0.0176（**动了**） |
| `gemini-3.8-flash`（`max_tokens=1`） | 132 | 0.0419 → 0.0435（**动了**） |
| `gemini-3.8-flash-tiered` | 150 | 0.0435 → 0.0502（**动了**） |

token 数不是原因——`max_tokens=1`、只回 132 token 的那次照样开窗；**模型**才是原因。2.5 / 3 / 3.1 / 3.5 的 flash 家族不动这个计数（大概不在池内计费），只有 `gemini-3.8-flash` 及其 `-tiered` 动。

代价正是本需求要避免的那种：最便宜的 flash-lite 每次回 200，窗口却还是「没用过」，于是每轮都再发一次首调——线上曾连着发出 176 次。所以挑法改成：

**`Gemini` 池**（`gemGeminiModel`）：

1. 账号列了 `gemini-3.8-flash` → 就问它；只有 `-tiered` 就问 `-tiered`。Antigravity 的 `-low` / `-medium` / `-high` 由 `antigravityBaseIn` 收敛成家族 id 再问，**不能直接问 `-low` / `-medium`**：实测这两个拿不到 usage，调用失败；
2. 账号一个 3.8 家族都没有 → 退回原来的「最便宜的 flash-lite」（`warmPick` 按 list price 挑，见 `internal/provider/codex_warmup.go:410-431`），至少还发得出去一次，老套餐仍有开窗机会；
3. 一个 gemini 模型都没有 → 记 `Err` 并跳过这个池，不发调用（PRD R2 第 4 条）。

**`Claude & GPT` 池**（`gemClaudeModel`）：优先 id 里带 `sonnet` 的，其次带 `claude` 的，再次 `gpt-oss`；同一档里按 list price 取最便宜的。实测 `claude-sonnet-4-6` 动这个池：5 小时 0 → 0.0015、7 天 0 → 0.0008，两个 `resetsAt` 都钉在调用时刻 + 窗口长度。

**`Gemini 4 Argon` 池**（`gemArgonModel`）：要 `gemini-4-argon` 本身；没有就取第一个以 `gemini-4-argon` 开头、且不是 `gemini-4-argon-disabled` 的 id。实测 `gemini-4-argon` 把这个池的 7 天从 0.2332 推到 0.2345，上游回的模型名是 `gemini-4-argon-trial`（它不在任何账号的列表里）。

**认不出的池**：不调，只记「未监视」，页面上仍然画出来（`gemPoolWatched`）。

实现见 `internal/provider/gemini_warmup.go` 的 `gemFlashFamily` / `gemModelFor` 与三个池各自的挑选函数，注释里都记着对应的实测。候选一律只看账号自己列的模型（`gemModels`，账号自己的表优先，退到 provider 的合并表），不写死名字：套餐没列的模型问过去只会被拒（pix 账号：「X-Magpie-Account: y19913868365@gmail.com's plan doesn't list claude-sonnet-4-6」，它列的是 `claude-sonnet-5-5`），被拒同样不开窗。

> **为什么 `Gemini` 池不能顺手用 `claude` / `gpt-oss`**：它们属 `Claude & GPT` 池（`internal/provider/google.go:1264-1272` 按 family 归组），开的是**另一个**池的窗——那个池该由它自己的模型去开。反方向也不成立：`gemini-4-argon` 同时会动 `Gemini` 池（实测），所以 Argon 不是隔离的那一头。

### 3.5 成功与失败

| 情形 | 处理 | 下一轮 |
| --- | --- | --- |
| HTTP 200 | 记 `LastCallAt = now`、`Status = 200`；清 `Err` | 下一轮重读，应看到 `Used > 0`，不再开窗 |
| HTTP 429 / 5xx | 记 `Status`、`Err`；不发下一次 | 按随机间隔重试（N 是上界） |
| 网络错误 / 超时 | 同上，`Status = 0` | 同上 |
| 账号在休息（`pinTo` 返回 429） | 记 `Err`；**不 `wbWake` 式解冻** | 同上 |
| 没有 gemini 模型 | 记 `Err` | 仍按间隔重读（模型表可能变） |

**不做指数退避**：WorkBuddy 用 12 小时预算 + 5–15 分钟随机（`internal/provider/workbuddy_warmup.go:40-47`）是因为它在等一个**已知的重置时刻**。Gemini 这里没有「等」——每轮都是重新读一次上游，读到的永远是当下的事实。用固定上界的随机间隔就够，退避只会让「窗口刚重置、正好没人用」的这段空档被错过。

### 3.6 与现有机制的关系

| 机制 | 关系 |
| --- | --- |
| `LoginUsage` 的 1 分钟缓存（`internal/provider/login_usage.go:178`） | 本循环自己的读取会命中缓存，因此**实际打到上游的频率不会超过每分钟一次**，即使 N 配到 1 分钟 |
| `StaleAllowance`（`internal/provider/routing.go:678`） | 开窗调用之后调一次，让下一次 `Allowances` 重新问上游，而不是信任开窗前的旧读数 |
| `KeepCodexWindowsWarm` / `KeepClaudeWindowsWarm` / `KeepWorkBuddyWarm` | 完全独立，互不影响；三个循环各自有自己的设置开关 |
| `WatchQuotas`（`internal/provider/quota_alert.go:261-290`） | 它只读额度、从不调模型；本循环是唯一会主动调模型的 Gemini 路径 |
| `QuotaReads == "asked"`（设置「额度只在被问时读」） | **必须显式传 `provider.Asked(ctx)`**，见 §3.7 |
| 路由与 `Rest` | 不新增 `Rest` 原因，不改 `pinTo`；开窗调用被拒时就是被拒，如实记录 |

### 3.7 与「额度只在被问时读」这个设置的关系

`LoginUsage` 的读取本身是**被这个设置管住的**：`internal/provider/login_usage.go:171-178` 在 `holding(ctx)` 为真时直接返回缓存（`held || time.Since(e.at) < time.Minute`，缓存永不过期），一条缓存都没有时返回 `errNotAsked`（`internal/provider/login_usage.go:197`）。而 `holding` 的口径是「不是用户要的读」——`internal/provider/quota_asked.go:48` `heldRead(ctx) = !wasAsked(ctx) && readsAsked()`。

**后果**：若循环用一个普通 ctx 去读，在 `QuotaReads == "asked"` 时读到的是**旧读数**（或 `not read yet` 错误），而旧读数里那个 `Used == 0` 可能早就不成立了 —— 循环会以为「还没用过」，**每个 tick 都开一次窗**。

**处理**：循环的读取用 `provider.Asked(ctx)` 包一层：

```go
q := LoginUsage(Asked(ctx), "antigravity")[user]  // 同在 package provider 内
if q.Error != "" {
    s.Err = q.Error
    continue // 读数不可信时不动手，与 internal/provider/codex_warmup.go:156-158 同一处理
}
```

理由：用户把这个开关打开，就是明确要求 magpie 定时去读；这不是「没人问的读」。`Asked` 的作用正是把一次读声明成用户要的（`internal/provider/quota_asked.go:30-33`），`holdUnasked` 因此不再扣住它（`:52-57`）。

> **一处待观察**：`docs/subsystems/providers-accounts.md:44` 写「Warm-up and check-in are not reads and are unchanged」，但 Codex 的 warm-up 是通过同一个 `LoginUsage` 读的（`internal/provider/codex_warmup.go:354`），并未传 `Asked`，因此在 `asked` 下同样会被扣住。这是既有行为，**不在本需求范围**，只记录不修改。

### 4.1 服务端路由（新）

`internal/gui/gemini_custom.go`（新文件），挂在 `internal/gui/api.go` 的 `workbuddyCustomRoutes(mux)`（`:1127`）旁边，照它的形状：

```go

if in.Every != 0 && in.Every < min {
    http.Error(rw, "every is at least "+strconv.Itoa(min)+" seconds", http.StatusBadRequest)
    return
}
```

`every == 0` 是合法值，表示「用默认」，所以校验必须是 `!= 0 && < min`，不能写成 `< min`。

### 4.4 汇总 / 详细信息 用哪些接口

两块视图都复用现有 usage 接口，不新增聚合端点。

| 视图 | 请求 | 依据 |
| --- | --- | --- |
| **详细信息**（逐条请求） | `GET /api/usage/requests?period=last:5h&account=<user>&provider=antigravity` | `internal/gui/usage.go:104-108`；筛选参数全支持 `internal/usageapi/usageapi.go:167` `FilterOf`（含 `account` / `provider`）；过滤真正生效于 `internal/usage/ledger.go:171` 与 `internal/usage/request_page.go:1072`（`out.Sum.addRow(r)` 只在 `f.keepsRow(r)` 时执行，所以**连汇总数字都是过滤后的**） |
| **汇总**（该账号该区间） | `GET /api/usage/requests?period=last:5h&account=<user>&provider=antigravity&limit=1` | **因为 `GET /api/usage` 不支持账号筛选**（见下），只能从 ledger 的 `Totals` 取 |

#### 已知偏差 1：`GET /api/usage` 忽略 `account` / `provider`

`internal/gui/usage.go:100-102` 的实现是：

```go
mux.HandleFunc("GET /api/usage", func(rw http.ResponseWriter, r *http.Request) {
    writeJSON(rw, usageState(periodOf(r.URL.Query().Get("period"))))
})
```

只读 `period`，把结果直接交给 `usageapi.Page`（`internal/gui/usage.go:34` `usageState = usageapi.Page`），而 `Page` 的签名只收 `Period`（`internal/usageapi/usageapi.go:75`）。**传 `account` 会被静默忽略**，返回的是全量汇总，用它当「该账号的汇总」会给出错误的数字。

**处理**（本设计采纳）：汇总视图从 `/api/usage/requests` 的响应里取 `Totals` —— `Ledger` 结构内嵌了 `usage.Totals`（`internal/usageapi/usageapi.go:210`，字段被 JSON 打平；合计在 `:274` `Totals: l.Sum`），而它的数字是**按 filter 过滤后**累加的（`internal/usage/request_page.go:1062`（`keep := f.keepsRow(r)`）与 `:1072`（`out.Sum.addRow(r)`））。`limit=1` 让响应只带一行，但 `Totals` 与 `Total` 仍是全量。

> **取数的形状**：`usage.Totals` 是**匿名内嵌**（`internal/usageapi/usageapi.go:210`），Go 的 JSON 编码会把它的字段**打平**到 `Ledger` 这一层——响应里是顶层的 `calls` / `errors` / `input` / `output` / `cache_read` / `cache_write` / `cost` / `unpriced`（标签见 `internal/usage/usage.go:382-412`），**没有 `sum` 这层包装**。前端要读 `ledger.calls`、`ledger.input`，不能读 `ledger.sum.calls`。

> 若后续要一个真正的账号级汇总端点，那是一次独立改动（新增接受 `usage.Filter` 的 `Summarize` 变体），不在本轮范围内。

#### 已知偏差 2：`last:7d` 不合法

`Period.Last()` 用 `time.ParseDuration` 解析（`internal/usage/period_range.go:46-56`），它支持 `h` / `m` / `s`，**不支持 `d`**。`last:7d` 解析失败返回 0，`Known()` 为假（`internal/usage/period_range.go:80-86`），`usageapi.PeriodOf` 于是静默降级为 `usage.Month`（`internal/usageapi/usageapi.go:160-165`），也就是 `30d` —— 用户要 7 天，拿到 30 天，而且没有任何提示。

测试已经把 `90d` 列在拒绝清单里（`internal/usage/period_last_test.go:80`）。

**处理**：7 天视图用 `period=last:168h`（`168 = 7×24`）。`last:5h` 本身合法，5 小时视图直接用。

> 这也是为什么汇总视图不能只把 `period` 交给 `/api/usage`：那个端点的 `periodOf` 对非法值同样是静默降级，而 `/api/usage/requests` 至少会把 `period` 原样回显在 `Ledger.Period` 里，页面可以据此发现「我要的不是这个」。

### 4.5 页面状态字段怎么读

`GeminiRow` 里 `Pools` 是这个账号的每个池（`gemPools`），每个池带自己那几扇 `Windows`，其中池窗口的 `Pool` / `Family` 已由 `internal/provider/google.go:1175` / `:1225` 填好。前端只需：

1. 每个池画自己的一行，名字是 `pool`；
2. 池内按 `name` 区分 `5 hours` / `7 days`（`internal/provider/google.go:1237,1239` 的赋值）；
3. 判定窗口是 5 小时那扇（没有就取 7 天那扇，`govOf`）：`used > 0` → 「窗口在用」，否则「还没被消耗」；
4. 池自己的 `model` / `lastCallAt` / `attempts` / `status` / `err` 画在池下面；`watched == false` 的池标「未监视」，不画调用信息。

## 5. 影响面与风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **A1 不成立** | 若 5 小时窗口其实是自然时刻重置，「定时开窗」毫无意义 | 阶段 0 先验证；不成立则整个需求停掉，只留展示 |
| **`Aside` 误用** | 照抄 `notStarted` 会把池窗口永远判成「已使用」（它 `Aside: true`），开窗一次都不发 | 自己的判定（`gemRead` + `governing()`，§3.2），并写单测：`Aside: true` 的池窗口 `Used == 0` 时被开窗 |
| **只有 7 天窗口的池** | `Gemini 4 Argon` 没有 5 小时桶，按 5 小时判就永远不开 | 判定窗口按池取（`governing()`：有 5 小时用 5 小时，否则 7 天），并写单测 |
| **认不出的池被误开** | 拿别的池的模型去调，开的是别的池的窗，还多花一次调用 | `gemPoolWatched`：认不出的池只画不调 |
| **`max_tokens` 不生效** | `internal/gateway/codeassist.go:384`：只有 Claude 会被转成 `maxOutputTokens`，gemini 模型上 `max_tokens` 被丢掉 | 靠提示词只有一个 `hi` 压短输出；真正要硬上限需改 `codeassist.go`，本轮不做（PRD A4） |
| **开窗调用被计成用户用量** | 它会进账本，若被当成账号自己的使用会污染统计 | `User-Agent: magpie-gemini-warmup/1` → `ByMagpie()` 为真（`internal/usage/usage.go:713-720`），页面按需过滤；与 WorkBuddy 的做法一致（`internal/gui/workbuddy_requests.go:107-115` `workbuddyDropProbes`） |
| **多实例重复开窗** | 两台 magpie 各自读到「未使用」，各开一次 | 状态文件是本机的；两次开窗的后果只是多一次极小调用，不是错误。若要严格，需把状态放共享存储——不在本轮 |
| **`pinTo` 拒绝导致误判为上游拒绝** | 账号在休息时，网关根本不发出去就 429 | `Err` 里带上 `Status`，日志区分「网关拒绝」与「上游拒绝」；与 `internal/provider/workbuddy_warmup.go:531-534` 的 `wbWake` 注释同一个坑，但 Gemini 不做 `wbWake` |
| **体积预算** | 新增脚本若进核心会顶破 `internal/gui/core_budget_test.go:18-19` 的 `appScriptBudget` / `coreScriptBudget` | 全部放在 `assets/plugins/gemini/` 下，不进核心预算 |
| **`asked` 模式下空转或狂开窗** | 读数被扣住时可能是旧的 `Used == 0`，导致每 tick 开一次窗 | 循环用 `provider.Asked(ctx)` 声明这是用户要的读；且 `q.Error != ""` 一律不动手（§3.7） |
| **i18n 漏词** | `TestBuiltinsTranslated`（`internal/gui/builtins_test.go:248`）要求清单里的 `Name` / `Sub` / `One` / `Many` 四种语言都有 | 四个 `i18n.js` 语言块都要加（`internal/gui/assets/i18n.js:6,3882,7743,11606`） |
