# REQ-002 · Gemini / Antigravity 定时开窗

> 状态：设计完成，待实现 · 2026-10-23
> 优先级：**P0**（本轮第一个实现的需求）
> 关联：`doc/gemini/产品需求文档.md`、`doc/gemini/技术设计文档.md`

---

## 1. 需求陈述

Antigravity 的 5 小时额度窗口**从重置后的第一次调用起算**，不是从重置那一刻起算。所以一个账号只要没人用，窗口就永远不开始，额度也永远不往前走；等到真要用的时候才开始 5 小时倒计时，等于把可用的 5 小时整体往后推。

一个账号的额度不是一份，而是按模型分成几个**池**（`Gemini`、`Claude & GPT`，部分套餐还有 `Gemini 4 Argon`），每个池有各自的窗口、各自的计时。只开一个池，等于只把那一份往后挪。

**要求**：

1. **定时**读取每个 Antigravity 账号**每个池**的用量；
2. 某个池**未使用**时，**立即用该池的一个模型发一次极小的真实调用**，把那个池的计时开起来；
3. 某个池**已使用**时不打扰，等下一个**随机间隔**再看；
4. 每个池的动作与读数分别留痕，可在页面上看到。

## 3. 设计决策（已确认）

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 「用过没有」怎么判 | **读上游额度**，5 小时窗口 `Used > 0` 即算用过 | 权威信号优先于本地推算；本地不知道用户是不是在别的机器上用过 |
| 开窗调用走哪条路 | **走本机网关** `POST /v1/chat/completions` | 只有走网关才进账本、才被路由、才可事后核对（PRD D2） |
| 开窗用什么模型 | **每个池各挑一个**，都从账号自己的模型列表里挑：`Gemini` 池仍是 `gemini-3.8-flash`（其次 `-tiered`，再次最便宜的 flash-lite）；`Claude & GPT` 池优先 `sonnet`，其次 `claude`，再次 `gpt-oss`，有价格时取最便宜；`Gemini 4 Argon` 池要 `gemini-4-argon` 本身，其次它的变体（`-disabled` 除外） | 开窗只需要「一次成功调用」，不需要产出，而**模型决定它动哪个池**：实测 `gemini-3.8-flash` 只动 `Gemini` 池（`Gemini 4 Argon` 的 7 天用量跨过这次调用没变），`claude-sonnet-4-6` 动 `Claude & GPT` 池，`gemini-4-argon` 动 `Gemini 4 Argon` 池。用错模型等于「调用成功、窗口没开」，下一轮又判成「没用过」再发一次（线上连发 176 次就是这么来的）。模型名必须来自账号自己的列表：pix 账号明确拒绝 `claude-sonnet-4-6`（「plan doesn't list claude-sonnet-4-6」），列的是 `claude-sonnet-5-5`。全表见 §5.5 与 `技术设计文档.md` §3.4 |
| 池怎么判「开过没有」 | 每个池看它**自己的判定窗口**：有 5 小时窗口就用 5 小时，没有就用 7 天 | 实测 `Gemini 4 Argon` 只有 7 天桶、**没有 5 小时桶**，按 5 小时判就永远判不出来、永远不开。判定还要落到**这个窗口自己**的用量上：5 小时重置回 0 而 7 天仍有用量时，不能读成「这个池已经开了」 |
| 间隔语义 | 配置值 N 是**上界**，实际 `rand(0.8N, N)` | 多账号不同步，避免同一分钟一起打上游；N=5 分钟时实际 4–5 分钟 |
| 默认间隔 | **5 分钟**（`GeminiWatchDefault()`） | 与额度告警的读取节奏同量级（`internal/provider/quota_alert.go:256` `quotaAlertEvery = 5*time.Minute`）；且小于 5 小时窗口，足够在窗口期内抓到「刚重置」 |
| 最小间隔 | **1 分钟**（`GeminiWatchMin()`） | 与 `LoginUsage` 的缓存 TTL 一致（`internal/provider/login_usage.go:178`）：再密也只会命中缓存，不会多打上游 |
| 失败重试 | **固定上界的随机间隔**，不做指数退避 | 每轮都是重新读一次上游，读到的是当下事实，没有「等一个已知时刻」这回事 |
| 认不出的池怎么办 | **只在页面上画出来，绝不调用**，并记下「未监视」 | 认不出池就认不出动它的模型；拿别的池的模型去调，开的是**别的**池的窗，还多花一次调用 |
| 账号范围 | 只 `agent == "antigravity"` 的账号 | 只有它有池窗口（`internal/provider/google.go:1184-1186`） |
| 关掉时 | 完全静止：不读、不调 | 用户关掉就该一点都不动 |

## 5. 行为规范

### 5.1 判定：这个池开过没有

```go
// gemPoolWindows is one of an account's pools and the windows it reports.
type gemPoolWindows struct{ Pool string; Five, Week *QuotaWindow }

// governing is the window whose own figure says whether the pool's clock is
// running: the 5-hour one where the pool has one, else the 7-day one.
func (p gemPoolWindows) governing() *QuotaWindow {
    if p.Five != nil { return p.Five }
    return p.Week
}
```

**一个池看哪个窗口**：有 5 小时窗口就看 5 小时，没有就看 7 天。实测 `Gemini 4 Argon` 只有 7 天桶、没有 5 小时桶，按 5 小时判就永远判不出来、永远不开。

**判定落到判定窗口自己的用量上**：一个池的两个窗口各有各的钟。5 小时窗口重置回 0、而 7 天窗口仍有用量时，那是「5 小时这一轮还没开始」，不是「已经开了」。

**为什么不能直接用 `notStarted`**：那个函数（`internal/provider/codex_warmup.go:655-657`）的第二个条件就是 `!w.Aside`，而池窗口在 `internal/provider/google.go:1234` 被构造为 `Aside: true`（语义是「用光它不会让账号停摆」，见 `internal/provider/subscription_usage.go:60-64`）。照抄的结果是**判定永远为假，一次开窗都不会发生**，而且不会报错——最难查的那类 bug。

**「没用过」不等于「读不到读数」**：池桶在 `internal/provider/google.go:1234` 以 `Used: 100` 起手（当作「用光」），只有拿到 `remainingFraction` 才改写（`:1250-1252`）。因此「上游没给读数」与「用光了」在结构上是同一个 `Used == 100`，靠**有没有 `resetsAt`** 区分（`gemRead`）：没有重置时刻的桶不是读数。

**所以一轮的判定顺序是**：`q.Error != ""` → 整个账号不动手；`gemRead(gov)` 为假 → 这个池没有读数，记下原因、不发调用；`gov.Used > 0` → 钟在走，什么都不做；`q.AsOf != nil`（读到的是旧读数）→ 不动手（§5.6）；否则用这个池的模型发一次。**宁可少开一次窗，不可把「读数坏了」当成「没用过」**。

### 5.2 定时轮询

后台循环，**每分钟 tick 一次**（与 `internal/provider/workbuddy_warmup.go:56` 的 `wbWarmEvery` 同量级）。tick 只决定「什么时候来看一眼」，真正的「什么时候该读某个账号」由每个账号自己的 `NextAt` 决定。

```
KeepGeminiWarm(ctx):
    ticker = every 1 minute
    for:
        select ctx.Done() -> return
        select ticker.C  ->
            w = current watch setting        // 每轮重读，改设置无需重启
            if !w.On: continue
            state = load(gemini-warmup.json)  // 读不出来就是空
            for user in antigravity accounts:        // googleLogins("antigravity")
                s = state[lower(user)]
                if now < s.NextAt: continue           // 没到点
                read(user)                            // §5.3
                s.NextAt = now + rand(0.8*N, N)
                state[lower(user)] = s
            save(gemini-warmup.json)                  // 原子写
```

**为什么 `NextAt` 存在状态文件里而不是内存**：进程重启（Docker `restart`、升级）后，如果 `NextAt` 只在内存里，所有账号会在重启瞬间同时到点、同时读、同时开窗——正是随机间隔想避免的事。落盘让重启后的节奏保持打散。

**为什么 tick 是 1 分钟而默认间隔是 5 分钟**：tick 是「最小可分辨时间」，必须不大于最小可配置间隔（1 分钟，`GeminiWatchMin()`）。若 tick 是 5 分钟，用户把 N 配成 1 分钟也不会生效。

### 5.4 首字调用

```go
const geminiCallTimeout = 60 * time.Second

func firstCall(ctx context.Context, account, model string) (int, error) {
    if url := gatewayURL(); url != "" {
        ctx, cancel := context.WithTimeout(ctx, geminiCallTimeout)
        defer cancel()
        body, _ := json.Marshal(map[string]any{
            "model":      model,
            "messages":   []map[string]string{{"role": "user", "content": "hi"}},
            "max_tokens": 1,
        })
        req, err := http.NewRequestWithContext(ctx, http.MethodPost, url+"/v1/chat/completions", bytes.NewReader(body))
        if err != nil { return 0, err }
        req.Header.Set("Content-Type", "application/json")
        req.Header.Set("X-Magpie-Account", account)        // 钉账号
        req.Header.Set("User-Agent", "magpie-gemini-warmup/1") // 账本里认成 magpie 自己的
        resp, err := http.DefaultClient.Do(req)
        if err != nil { return 0, err }
        defer resp.Body.Close()
        b, _ := io.ReadAll(io.LimitReader(resp.Body, 1<<16))
        if resp.StatusCode != http.StatusOK {
            return resp.StatusCode, fmt.Errorf("%s", strings.TrimSpace(string(b)))
        }
        return resp.StatusCode, nil
    }
    return 0, errors.New("the gateway's address isn't known yet")
}
```

三个头部分别解决三件事：

| 头部 | 解决什么 | 依据 |
| --- | --- | --- |
| `X-Magpie-Account` | 不让路由换人。换人开窗等于开了**别的账号**的窗 | `internal/gateway/gateway.go:6474`；钉住的账号在休息时 `pinTo`（`internal/gateway/fallback.go:3239`）直接 429，不替代 |
| `User-Agent: magpie-gemini-warmup/1` | 让这次调用在账本里被认成 magpie 自己的，不污染「这个账号用了多少」 | `internal/usage/usage.go:713-720` `ByMagpie()` |
| `max_tokens: 1` | 压短输出 | **注意**：Antigravity 的 gemini 模型上它不会被转发，见 §8 |

**超时 60 秒**，与 `internal/provider/workbuddy_warmup.go:60` 的 `wbWarmProbeTimeout` 一致：开窗请求只需要拿到 200，一个挂住的请求不是答案。

### 5.5 模型怎么挑

```
gemModelFor(user, pool):        // internal/provider/gemini_warmup.go
    ids = 账号自己列的模型，Antigravity 的 -low/-medium/-high 由
          antigravityBaseIn 收敛成家族 id
    switch pool:
    case "Gemini":              // 只有 3.8 家族动这个池
        if "gemini-3.8-flash" in ids:        return it
        if "gemini-3.8-flash-tiered" in ids: return it
        lite  = [id for id in ids if "flash-lite" in id]  // 一个 3.8 都没有时的退路
        if lite:  return cheapest(lite)                   // warmPick，按 list price
        flash = [id for id in ids if "flash" in id]
        if flash: return cheapest(flash)
        return 账号列的第一个 gemini id
    case "Claude & GPT":        // 实测 claude-sonnet-4-6 动这个池
        for want in ["sonnet", "claude", "gpt-oss"]:
            got = [id for id in ids if want in id]
            if got: return cheapest(got)
        return ""               // 这个账号没有能开这个池的模型
    case "Gemini 4 Argon":      // 实测 gemini-4-argon 动这个池
        if "gemini-4-argon" in ids: return it
        return 第一个以 "gemini-4-argon" 开头、且不等于
               "gemini-4-argon-disabled" 的 id
    default:
        return ""               // 认不出的池：不调（§3、§5.3）
```

**为什么不是最便宜的**：实测（150 上逐模型比 5 小时窗口 used 前后，全表见 `技术设计文档.md` §3.4）2.5 / 3 / 3.1 / 3.5 的 flash 家族**不动** Gemini 池的计数——`gemini-2.5-flash-lite` 发 2157 token 前后都是 0.0164，`gemini-3-flash` 发 1167 前后都是 0.0176；只有 `gemini-3.8-flash` 动（1325 token 动、97 token 动、`max_tokens=1` 只回 132 token 也动），`-tiered` 同样动。token 数不是判据，模型才是。挑便宜的等于「调用成功、窗口没开」，下一轮又判成「没用过」再发一次——线上连发 176 次就是这么来的。

**池和模型的对应是实测的，不是推的**（同一台 150：`max_tokens=1` 发一个 `hi`，用 `X-Magpie-Account` 钉账号，再重读一次额度）：`gemini-3.8-flash` 只动 `Gemini`，`Gemini 4 Argon` 的 7 天用量跨过这次调用仍是 0.2345；`claude-sonnet-4-6` 动 `Claude & GPT` 的 5 小时（0 → 0.0015）和 7 天（0 → 0.0008），**一次调用同时把两个窗口钉在调用时刻 + 5 小时 / + 7 天**；`gemini-4-argon` 动 `Gemini 4 Argon` 的 7 天（0.2332 → 0.2345），上游回的模型名是 `gemini-4-argon-trial`，而它同时也动 `Gemini` 池——所以 Argon 并不是反过来的隔离。

**不要直接问 `gemini-3.8-flash-low` / `-medium`**：实测这两个不返回 usage，调用失败。问家族 id，由网关按 effort 解析到变体（`AntigravityVariants`）。

**没有 3.8 家族的账号**仍退回最便宜的 flash-lite：至少发得出去一次，老套餐还有开窗的机会，虽然该模型是否计进池未经验证。

**模型名一律从账号自己的列表里取，绝不写死**：pix 账号（`y19913868365@gmail.com`）明确拒绝 `claude-sonnet-4-6`——「X-Magpie-Account: y19913868365@gmail.com's plan doesn't list claude-sonnet-4-6」——它列的是 `claude-sonnet-5-5`。写死名字的结果是那个池永远开不了，而且每次都多一次被拒的请求。

仓库已有同形的挑法可参照：`internal/provider/codex_warmup.go:410-431` `warmPick`（按 list price 挑 `Input + Output` 最小的，无价格时按名字退让）。

### 5.6 为什么读取要用 `Asked(ctx)`

`LoginUsage` 在 `QuotaReads == "asked"`（设置里选了「额度只在被问时读」）时会把「不是用户要的读」扣住：`internal/provider/login_usage.go:171-178` 只要 `holding(ctx)` 为真就直接返回缓存，缓存**不会过期**；一条缓存都没有时返回 `errNotAsked`（`:197`）。`holding` 的定义是 `heldRead(ctx) = !wasAsked(ctx) && readsAsked()`（`internal/provider/quota_asked.go:48`）。

**后果**：用普通 ctx 去读，在 `asked` 下拿到的是旧读数。旧读数里那个 `Used == 0` 可能早就不成立——循环会**每个 tick 都发一次开窗调用**，这是本设计最危险的一种失效方式（安静地多花钱）。

**处理**：读取时传 `provider.Asked(ctx)`（`internal/provider/quota_asked.go:30-33`），把它声明成用户要的读；`holdUnasked`（`:52-57`）因此不再扣住它。用户打开这个开关，本来就是要求 magpie 定时去读，不该被自己的设置扣住。

**并且**：`q.Error != ""` 时一律不动手（与 `internal/provider/codex_warmup.go:156-158` 的 `continue` 同一处理）。「读数不可信」绝不能等价于「窗口没开始」。

> 附带记录（不改）：`docs/subsystems/providers-accounts.md:44` 说「Warm-up and check-in are not reads and are unchanged」，但 Codex 的 warm-up 走的是同一个 `LoginUsage`（`internal/provider/codex_warmup.go:354`），未传 `Asked`，在 `asked` 下同样会被扣住。既有行为，不在本需求范围。

### 5.7 每个时刻常量的理由

| 常量 | 值 | 为什么是这个值 |
| --- | --- | --- |
| tick | 1 分钟 | 必须 ≤ 最小可配间隔（`GeminiWatchMin()` = 1 分钟），否则配小了不生效；与 `wbWarmEvery`（`internal/provider/workbuddy_warmup.go:56`）同量级，成本可忽略 |
| 默认间隔 | 5 分钟 | 与 `quotaAlertEvery`（`internal/provider/quota_alert.go:256`）同量级；5 小时内最多约 60 轮，足够在窗口重置后很快发现 |
| 最小间隔 | 1 分钟 | 与 `LoginUsage` 缓存 TTL 一致（`internal/provider/login_usage.go:178`）：再密也命中缓存，不会多打上游 |
| 随机下界 | 0.8 × N | 多账号必须错开；0.8 让实际间隔与用户预期不偏离太远（N=5 分钟 → 4–5 分钟） |
| 调用超时 | 60 秒 | 与 `wbWarmProbeTimeout`（`internal/provider/workbuddy_warmup.go:60`）一致；一个挂住的请求不是答案 |
| 每次最多开窗次数 | 1 | 一轮一次判定只发一次；判定成功后 `Used > 0`，下一轮自然不再发 |

**没有的常量**：没有重试预算，没有退避倍数，没有「放弃」标记。理由：本循环等的不是一个已知时刻，而是「上游说这个窗口还没开始」这个**当下事实**。只要事实还成立，就该开；事实一变（`Used > 0`），立刻停。WorkBuddy 那套 12 小时预算 + 指数退避（`internal/provider/workbuddy_warmup.go:40-47`）是为「等一个已经知道的重置时刻」设计的，形状不同。

### 5.8 与现有机制的关系

- **不改** `Allowances`（`internal/provider/routing.go:484`）的取舍；
- **不改** `Rest` / `restingUntil` 的语义，不新增 `Rest.Why`；
- **不改** `pinTo`（`internal/gateway/fallback.go:3239`）：被拒就是被拒，如实记录；
- **会调** `StaleAllowance`（`internal/provider/routing.go:678`）：开窗成功后让下一次额度读取重新问上游，而不是信任开窗前的旧读数；
- **与** `KeepCodexWindowsWarm` / `KeepClaudeWindowsWarm` / `KeepWorkBuddyWarm` **完全独立**，各有各的开关；
- **与** `WatchQuotas`（`internal/provider/quota_alert.go:261-290`）**不重叠**：它只读额度、从不调模型；本循环是唯一会主动调模型的 Gemini 路径。

## 7. 边界与不做

- **不做** 有 5 小时窗口的池的「7 天单独开窗」：一次调用同时把两个窗口钉住（实测 `claude-sonnet-4-6`），开 5 小时即覆盖。**只有**没有 5 小时窗口的池（Argon）才由 7 天窗口判定；
- **不做** 认不出的池的开窗：只在页面上画出来并记「未监视」；
- **不做** 本地用量推算（「大概用掉了多少」）——只读上游；
- **不做** 多 magpie 实例的协调（状态是本机的；两台各开一次窗的后果只是多一次极小调用）；
- **不做** 指数退避与放弃标记（理由见 §5.7）；
- **不做** 对已开窗账号的保活（那是 `KeepCodexWindowsWarm` 的语义，不是这里的）；
- **不改** 路由、`Rest`、额度卡片渲染。

## 8. 风险

| 风险 | 缓解 |
| --- | --- |
| 5 小时窗口其实是自然时刻重置（PRD A1 不成立） | 整个需求失去意义；阶段 0 先验证，不成立就停在这里，只留展示 |
| 照抄 `notStarted` 导致永远判成「已使用」 | 自己的 `geminiNotStarted`；单测第 3 条专门守这个 |
| `max_tokens` 在 Antigravity 的 gemini 模型上不生效 | `internal/gateway/codeassist.go:384` `if r.MaxTokens > 0 && (!ag || claude)`：只有 Claude 会被转成 `maxOutputTokens`。开窗请求靠「内容只有一个 `hi`」压短输出；要硬上限需改 `codeassist.go`，本轮不做 |
| 账号在休息时网关直接 429，被误读成「上游拒绝」 | `Err` 带 `Status`，日志里区分；且**不做** `wbWake`（WorkBuddy 那样先把账号唤醒再探），避免把一个不该被解冻的账号解冻 |
| 开窗调用被算成用户用量 | `User-Agent` 让 `ByMagpie()` 为真（`internal/usage/usage.go:713-720`），页面按需过滤；与 WorkBuddy 的 `workbuddyDropProbes`（`internal/gui/workbuddy_requests.go:107-115`）同一手法 |
| 两台 magpie 同时开窗 | 只是多一次极小调用，不是错误；严格化需共享状态存储，不在本轮 |
| 上游把「没给读数」和「用光了」都给成 `Used == 100` | 判定同时要求 `ResetsAt == nil` 与 `ResetSecs <= 0`（§5.1），宁可少开一次 |
| 上游改了池的组名（`Gemini` 不再是这个字符串），或加了一个新池 | 认不出的池不调用，页面上标「未监视」并记下原因；`Gemini` 池自己没了 5 小时桶时，退回用它的 per-model 窗口（`Family == "Gemini"`）里最紧的那个判定 |
| `asked` 模式下读到旧读数，每 tick 都开窗 | 读取传 `Asked(ctx)`（§5.6）；`q.Error != ""` 时不动手 |
| 开窗后上游读数仍报 `Used == 0`（窗口没被启动） | 下一轮会再发一次，直到读数变化。这正是「以事实为准」的代价：如果上游根本不认这次调用，会持续每分钟一次——因此需要观察第 13 条验收，若发现不生效，应加一个「同一次重置只开一次窗」的记录位（本轮不做，见 §7） |
